# Requirements, Acceptance Criteria and Traceability

## Make requirements testable
Rewrite vague requirements as observable outcomes. Define actors, preconditions, inputs, expected outputs, state changes, permissions, error behavior, and relevant boundaries.

## Acceptance criteria
Use examples or Given/When/Then where useful. Include positive, negative, boundary, authorization, validation, concurrency, and recovery cases when relevant. Criteria must be agreed by the authorized product or technical owner.

## Traceability
Map each requirement or risk to test cases and evidence. Stable identifiers are preferred. Traceability should show uncovered requirements and tests with no clear purpose; it is not a target for 100% paperwork.

## Change control
When requirements change, identify affected tests and update them deliberately. Do not change expected results merely to match implementation without confirming the requirement.

## Ambiguity
Record unresolved questions and assumptions. Do not invent product behavior or silently treat assumptions as approved requirements.
